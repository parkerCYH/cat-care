# 貓咪管理(Cat Settings)UI 規格

> 適用範圍:純手機版網頁,視窗寬度以 375px 為最小基準、430px 為上限,不考慮平板/桌面版面。導覽方式與[首頁](./home.md)一致,採右上角漢堡選單,不用底部 tab bar。屬於低頻功能,收在漢堡選單裡,不出現在首頁主要動線上。

## 1. 頁面定位

管理「貓咪」這個實體本身(新增、編輯基本資料)以及「誰能共同照護這隻貓」(`cat_players` 多對多關聯的邀請/移除)。因為是低頻操作,不追求步驟極簡,但仍要維持與其他頁面一致的手機版操作手感。

## 2. 版面結構:每個步驟都是獨立頁面

貓咪管理牽涉多個步驟(列表 → 詳情 → 編輯/新增/邀請),全部採**獨立頁面 + 返回上一頁**處理,不使用彈出式面板或對話框(與首頁記錄流程的導覽方式一致,原因同樣是手機瀏覽器對浮動元件的處理不穩定)。頁面對應的路由:

| 路由 | 內容 |
|---|---|
| `/cats` | 貓咪列表 |
| `/cats/:id` | 單一貓咪詳情(基本資料 + 共同照護者) |
| `/cats/new` | 新增貓咪 |
| `/cats/:id/edit` | 編輯貓咪基本資料 |
| `/cats/:id/invite` | 邀請共同照護者 |

### 2.1 `/cats`:貓咪列表頁

```
┌─────────────────────────────┐
│ ← 返回   貓咪管理         ☰   │
├─────────────────────────────┤
│ 🐱 小橘                    ›  │  ← 卡片列表,點擊進入單一貓咪詳情
│ 🐱 小黑                    ›  │
├─────────────────────────────┤
│      [ + 新增貓咪 ]           │  ← 固定在列表下方或頂部列右側
└─────────────────────────────┘
```

- 每張卡片顯示:貓咪頭像/預設圖示、名字,右側箭頭表示可點擊進入
- 卡片觸控區域整張可點擊,高度建議 ≥ 56px
- 「新增貓咪」為明顯的主要動作按鈕,位置固定(建議放在列表最下方,列表長時仍可捲動到達,或另外評估放在頂部列右側 icon)
- 只有一隻貓時,仍顯示列表(維持畫面一致性),不做「只有一隻貓就跳過列表」的特例

### 2.2 `/cats/:id`:單一貓咪詳情頁

```
┌─────────────────────────────┐
│ ← 返回   小橘              ☰  │
├─────────────────────────────┤
│ 基本資料                      │
│  名字:小橘                   │
│  出生日期:2020-05-01          │
│  備註:腎臟病控制中             │
│           [ 編輯基本資料 ]     │
├─────────────────────────────┤
│ 共同照護者                    │
│  👤 owner@example.com (你)    │
│  👤 friend@example.com        │
│           [ + 邀請共同照護者 ] │
└─────────────────────────────┘
```

- **基本資料區塊**:唯讀顯示 name、birthdate、notes,點擊「編輯基本資料」導向 `/cats/:id/edit` 進行編輯
- **共同照護者區塊**:
  - 列出目前所有 `cat_players`,每筆顯示 email(或顯示名稱),自己的帳號標示「(你)」
  - 每筆旁邊提供「移除」動作(除了自己以外都可移除;移除自己視為「退出共同照護」,需要二次確認)
  - 「+ 邀請共同照護者」導向 `/cats/:id/invite`,輸入 email 送出邀請

## 3. 互動細節

### 3.1 `/cats/new`:新增貓咪

- 獨立頁面,頂部列同樣有返回箭頭(取消新增,回到 `/cats`)
- 欄位:名字(必填)、出生日期(選填)、備註(選填),頁面底部固定「送出」按鈕
- 送出後直接導向新貓咪的詳情頁 `/cats/:id`,並提示「已新增,可以邀請其他照護者」

### 3.2 `/cats/:id/invite`:邀請共同照護者

- 獨立頁面,單一 email 輸入框 + 送出按鈕
- 送出後返回 `/cats/:id`,列表以 Optimistic UI 立即顯示「邀請中」狀態的項目(尚未接受邀請前的視覺標示,例如淡色 + 「邀請中」文字),等後端確認後轉為正常樣式
- 若 email 尚未註冊帳號、或送出失敗,停留在本頁顯示錯誤訊息並保留輸入內容,方便使用者修正重送

### 3.3 移除共同照護者

- 點擊「移除」→ 彈出確認對話框(「確定要移除 xxx 的照護權限嗎?」)→ 確認後才送出 API
- 這是本規格中少數仍用對話框(而非獨立頁面)確認的操作,因為只是單一是/否決定,不涉及輸入欄位;誤刪會影響到其他使用者的存取權,後果比記錄類操作更嚴重

### 3.4 `/cats/:id/edit`:編輯貓咪基本資料

- 獨立頁面,同新增邏輯,欄位預填現有資料
- 送出後返回 `/cats/:id`

### 3.5 刪除貓咪

- 本規格暫不涵蓋(涉及連動刪除該貓的所有排便/體重紀錄,風險較高,待後續規劃時再確認是否需要、以及要不要用「封存」取代「刪除」)

## 4. 待確認/開放問題

- 刪除貓咪的流程是否需要?若需要,是「封存(軟刪除)」還是「硬刪除」,以及是否需要輸入貓咪名字二次確認等高風險操作的防呆設計
- 邀請 email 尚未註冊帳號時,後端行為為何(先建立邀請紀錄等待註冊後生效?或直接拒絕)?需要對照 `auth` service 與 `cat_players` 的後端邏輯才能定案前端提示文字
- 貓咪頭像目前假設用預設圖示,若要支援上傳照片,涉及圖片上傳/裁切流程,不在本輪規格範圍內
