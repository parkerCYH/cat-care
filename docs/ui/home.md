# 首頁(快速記錄)UI 規格

> 適用範圍:純手機版網頁,視窗寬度以 375px(iPhone SE/mini 級距)為最小基準,最大以 430px(iPhone Pro Max 級距)為上限。不考慮平板/桌面版面。

## 1. 頁面定位

首頁是整個 app 唯一的預設進入點,也是使用頻率最高的畫面。核心目標只有一個:**讓「記一筆」這件事在最少點擊次數內完成**。所有次要資訊(歷史紀錄、貓咪管理)都收斂到這個畫面之外。

## 2. 版面結構(由上到下)

```
┌─────────────────────────────┐
│ 頂部列                 ☰ 選單  │  ← 貓咪切換器(單貓時隱藏)+ 右上角漢堡選單
├─────────────────────────────┤
│                               │
│   [ 記一筆排便 ]  大按鈕       │  ← 佔螢幕寬度,高度足夠大拇指單手觸控
│                               │
│   [ 記一筆體重 ]  大按鈕       │
│                               │
├─────────────────────────────┤
│ 最近紀錄摘要                  │  ← 今天/昨天各一行,一眼看出貓咪今天狀況
│  · 今天 07:30 排便 正常        │
│  · 今天 08:00 體重 4.2kg       │
└─────────────────────────────┘
```

**導覽方式改為右上角漢堡選單(不用底部 tab bar)**:手機瀏覽器的網址列會隨滾動方向顯示/隱藏,導致固定在畫面底部的 tab bar 跟著跳動、位置不穩定,體驗比原生 app 差。改用頂部列右上角的漢堡選單,點擊展開後以全螢幕或側邊抽屜(drawer)列出「排便歷史」「體重歷史」「貓咪管理」等入口,並固定在頂部,不受瀏覽器 UI 收合影響。

## 3. 各區塊細節

### 3.1 頂部列(Header)

- 左側:貓咪名稱(若多貓,點擊展開下拉/切換 tab;單貓時只顯示名字,不做任何切換 UI)
- 右側:漢堡選單 icon(☰),點擊展開導覽選單(見 3.4)
- 高度建議 48–56px,固定在頂部(sticky),避免使用者往下滑動時失去操作入口

### 3.2 快速記錄按鈕(核心區塊)

**共同規格:**
- 兩個按鈕垂直排列,各自佔滿螢幕可用寬度(左右各留 16px padding)
- 按鈕高度建議 ≥ 72px(遠大於一般按鈕,方便單手大拇指觸控,且視覺上強調「這是最重要的動作」)
- 按鈕內文字 + icon:例如「💩 記一筆排便」「⚖️ 記一筆體重」,字級建議 18–20px
- 兩按鈕之間留白約 12–16px,避免手滑誤觸

**「記一筆排便」按鈕互動流程:**
1. 點擊 → 立即以 Optimistic UI 顯示「已記錄」狀態(例如按鈕短暫變成打勾 + 成功提示 toast),背景送出 API
2. 預設時間 = 現在,預設無異常旗標、無備註 → 這是「兩步完成」的路徑:點擊即送出,不需要任何額外確認畫面
3. 若使用者想記錄形狀/異常/備註等進階欄位,點擊按鈕上的「展開」小箭頭圖示,導向獨立頁面 `/bowel/new`:
   - 時間(可調整,預設當下時間)
   - 形狀(選項式,例如正常/偏軟/偏硬/異常,用 chip 選擇而非下拉)
   - 是否異常(toggle)
   - 備註(單行文字,選填)
   - 頁面底部固定「送出」按鈕,送出後返回首頁
4. API 失敗時:Toast 顯示「記錄失敗,點擊重試」,並保留這筆記錄在畫面上標示為「待重試」狀態,不會憑空消失

**「記一筆體重」按鈕互動流程:**
1. 點擊 → 導向獨立頁面 `/weight/new`(體重一定要輸入數字,不能像排便一樣純點擊送出)
2. 頁面開啟時數字鍵盤(inputmode="decimal")直接跳出,輸入框自動 focus
3. 量測方式為下拉選單,預設值 = 使用者上次選過的選項(記憶在 local storage 或使用者設定)
4. 送出後同樣走 Optimistic UI:返回首頁、按鈕/摘要區立即顯示新紀錄,背景送出 API
5. API 失敗處理同排便按鈕邏輯

> **導覽方式說明**:排便/體重的進階輸入一律用「導向獨立頁面(有自己的 URL)+ 返回上一頁」處理,不使用彈出式面板或對話框。原因與捨棄底部 tab bar 一致——手機瀏覽器對浮動/固定定位元素的處理不穩定,獨立頁面才有可靠、可分享、可用瀏覽器上一頁鍵返回的行為。

### 3.3 最近紀錄摘要

- 顯示「今天」與「昨天」各自最新一筆排便 + 一筆體重(最多 4 行)
- 每行格式:`時間 + 類型 icon + 簡短內容`,例如:
  - `今天 07:30　💩 正常`
  - `今天 08:00　⚖️ 4.2kg`
- 異常紀錄以顏色/icon 標示(例如紅點),不需要點擊進入即可辨識
- 這個區塊只做「摘要」,不做互動(點擊不進入編輯),點擊整個區塊才導向對應的歷史列表頁

### 3.4 導覽選單(漢堡選單)

- 點擊頂部列右上角的 ☰ icon 後,以側邊抽屜(drawer,從右側滑出)或全螢幕覆蓋層展開選單,避免佔用畫面常駐空間
- 選單項目:首頁、排便歷史、體重歷史、貓咪管理、使用者頭像/帳號資訊(登出等)
- 每個項目觸控區域建議高度 ≥ 48px,方便單手操作
- 選單本身不隨頁面捲動而跳動(因為只在點擊時才出現,關閉後回到一般頁面捲動狀態),避免底部 tab bar 因瀏覽器網址列顯示/隱藏而跟著跳動的問題

## 4. 空狀態:尚未加入任何貓咪

使用者登入後,若還不屬於任何 `cat_players`(沒有貓咪、也沒人邀請),首頁不顯示快速記錄按鈕與紀錄摘要,改為顯示引導畫面:

```
┌─────────────────────────────┐
│ 頂部列                 ☰ 選單  │
├─────────────────────────────┤
│                               │
│           🐱                 │
│      還沒有任何貓咪            │
│  新增一隻貓咪就可以開始記錄了    │
│                               │
│      [ + 新增貓咪 ]           │
│                               │
└─────────────────────────────┘
```

- 頂部列與漢堡選單維持顯示(使用者仍需要能登出或查看帳號),只有中段的快速記錄區與摘要區被引導畫面取代
- 「+ 新增貓咪」按鈕導向獨立頁面 `/cats/new`([貓咪管理](./cat-management.md)的新增貓咪流程),完成後返回首頁,此時首頁應已轉為一般狀態(顯示快速記錄按鈕)

## 5. Optimistic UI 的視覺回饋規則

因為「摩擦力最小化」是整份規劃的核心原則,失敗回饋的視覺設計同樣重要,避免使用者因為看不到明確狀態而重複操作:

| 狀態 | 視覺回饋 |
|---|---|
| 點擊送出瞬間 | 按鈕短暫顯示 loading spinner(< 300ms 內,若 API 回得夠快甚至感覺不到) |
| Optimistic 成功(尚未等到 API 回應) | 按鈕/摘要區立即顯示新紀錄,右上角小圖示標示「同步中」 |
| API 真的成功 | 「同步中」圖示消失,紀錄變成一般樣式 |
| API 失敗 | 紀錄保留但標示為「待重試」(例如淡色 + 警示 icon),提供「點擊重試」動作 |

## 6. 待確認/開放問題

- 「今天/昨天」摘要要顯示到幾筆?目前假設各類型各顯示最新一筆,若使用者一天記錄多次排便,是否需要都列出來?
- 排便的「形狀」選項具體要有哪幾種(需要對照後端 `bowel_movements` 的欄位定義,目前規劃文件只寫「形狀/異常旗標」,尚未列舉列舉值)
- `/bowel/new`、`/weight/new` 頁面上使用者按瀏覽器返回鍵離開時,是否需要二次確認(避免誤觸離開遺失輸入內容)?
